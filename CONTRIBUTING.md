# Contributing to the lab 🦦

Thanks for being here. Technology is better when we build it together, and that includes how this repo is built.

You don't need to be an expert. You don't even need to know Git. If you can write about something you made, you can contribute.

## Ways to contribute

| I want to... | Do this |
|---|---|
| Show something I built | Post a Project Card on Discord, **or** open a [Share a project](../../issues/new?template=share-a-project.yml) issue, **or** open a pull request |
| Ask for help | Ask on Discord (`#ask-for-help`), or open an [Ask for help](../../issues/new?template=ask-for-help.yml) issue |
| Fix a typo, link or step | Open a pull request (the pencil icon on any file does it in your browser) |
| Suggest an idea | Open a [Suggest an improvement](../../issues/new?template=suggest-improvement.yml) issue |
| Report a problem | Open a [Report a problem](../../issues/new?template=report-a-problem.yml) issue |
| Help others | Answer questions on Discord and in issues. This is a contribution too |

## Your first pull request, step by step

A pull request is a way to say "here's a change, would you add it?" If you get stuck on any step, say so on Discord or in the PR. Someone will walk you through it.

1. **Fork the repo.** Click **Fork** at the top right. This makes your own copy.
2. **Copy the template.** In your fork, open `projects/_template/README.md`, copy it into a new folder named after your project: `projects/<your-project-name>/README.md` (lowercase, hyphens, for example `expense-tracker`). You can do this in your browser with **Add file, Create new file**.
3. **Fill it in.** Follow the Project Card. Required: name, one-liner, category, status, what it does, and the "safe to share" tick. Everything else is optional.
4. **Add pictures (optional).** Put them in `projects/<your-project-name>/screenshots/`.
5. **Open the pull request.** Click **Contribute**, then **Open pull request**, and fill in the short checklist.
6. **Reply to feedback.** A maintainer will reply within about three days with something kind and specific. Must-fix items are limited to: the safe-to-share check, the license, broken links and the required fields. Everything else is a suggestion, never a blocker.

## Safe to share (always)

Never put in any file, image or commit message: passwords, API keys, tokens, private keys, `.env` contents, recovery codes, your home's public IP address, or anyone's private information.

If you slip, it's okay. Rotate the key first (deleting the file is **not** enough, because the history keeps it), then tell a maintainer. Nobody gets shamed.

## Licenses and who owns what

- **You keep the copyright** to what you write.
- By submitting, you confirm that you wrote it or have the right to share it, that it has no secrets or private data, and that OtterLab may show it, with credit to you, in this repo, on Discord, on the website and in social posts.
- Choose a license for your project. **MIT** is a fine, beginner-friendly default for code. Use **CC BY 4.0** for a written guide. Not sure? Pick MIT and say so in the README.
- Credit your sources. If you used someone else's code, guide or idea, link them.
- Used an AI assistant? Great. Say so in the card, and make sure you've run what it wrote.

(This is a starting point, not legal advice.)

## Style: keep it friendly and plain

- Short sentences. Explain jargon the first time you use it.
- Say what it does before how it works.
- Pictures and examples beat paragraphs.
- Be kind in every comment, review and issue. The [Code of Conduct](CODE_OF_CONDUCT.md) applies.

## Reviewing as a maintainer

- First reply within 3 days: one specific compliment, then any must-fix items.
- Never block a project on taste or on how someone chose to build it (including AI help).
- Check the safe-to-share box and screenshots first. If a secret slipped in, handle it before anything else (label `safety`, remove, point the author to the rotate-your-key steps).
- Thank every contributor in the merge comment.
